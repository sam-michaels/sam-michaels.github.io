THE MATH

Why 30 ms, and why F1

Boundary detection has no natural notion of "close enough" — so the metric defines one. Scoring is a bipartite matching problem: predictions on one side, ground truth on the other, an edge wherever |p − g| ≤ τ. I solve it greedily nearest-first, which is optimal here because the matching graph is effectively an interval graph when τ is smaller than the minimum inter-boundary gap.

F1 is the right summary because the failure modes are asymmetric and equally costly: a model that fires constantly wins recall, one that never fires wins precision. The harmonic mean punishes both.

THE SIGNAL PROCESSING

What the spectrogram shows

Switch to the spectrogram view and the problem becomes visible. Horizontal bands are formants — vocal tract resonances that shift as the articulators move between vowels. The finely-spaced horizontal striations are harmonics of the glottal source at F₀.

Syllable boundaries are the vertical discontinuities: a broadband onset transient followed by a jump in formant trajectory. That is exactly the structure a frame-level classifier over transformer features has to learn to localise — and why 64 ms of spectral context per frame matters.

THE STATISTICS

Proving the gain was real

An F1 jump from 0.42 to 0.77 across six subjects could still be noise. Under leave-one-run-out cross-validation each subject yields a paired baseline/treatment score, so a paired test is the correct instrument: p = 0.016.

The p-value only says the effect exists. Cohen's d = 2.61 says it is enormous — the distributions barely overlap. Reporting effect size alongside significance is the difference between a result and a claim.

segmentation_head.py — the module that produced the 0.42 → 0.77 gainPyTorch 
class SyllableSegmentationHead(nn.Module):
    """Frame-level boundary classifier over frozen VG-HuBERT features.

    Boundaries are rare (~4% of frames), so a plain BCE loss collapses to
    the all-negative solution. Two fixes: a dilated temporal context stack
    so each frame sees ~200ms either side, and focal loss to stop the easy
    negatives from dominating the gradient.
    """

    def __init__(self, d_model=768, hidden=256, dilations=(1, 2, 4, 8)):
        super().__init__()
        self.context = nn.ModuleList([
            nn.Conv1d(d_model if i == 0 else hidden, hidden,
                      kernel_size=3, padding=d, dilation=d)
            for i, d in enumerate(dilations)
        ])
        self.norm = nn.ModuleList([nn.GroupNorm(8, hidden) for _ in dilations])
        self.proj = nn.Conv1d(hidden, 1, kernel_size=1)

    def forward(self, feats):                  # (B, T, 768) frozen encoder output
        x = feats.transpose(1, 2)                # (B, 768, T)
        for conv, norm in zip(self.context, self.norm):
            x = F.gelu(norm(conv(x))) + (x if x.shape[1] == norm.num_channels else 0)
        return self.proj(x).squeeze(1)          # (B, T) boundary logits


def focal_bce(logits, targets, alpha=0.25, gamma=2.0):
    # Down-weights the ~96% of frames that are trivially non-boundary.
    p  = torch.sigmoid(logits)
    ce = F.binary_cross_entropy_with_logits(logits, targets, reduction="none")
    p_t = p * targets + (1 - p) * (1 - targets)
    a_t = alpha * targets + (1 - alpha) * (1 - targets)
    return (a_t * (1 - p_t).pow(gamma) * ce).mean()

def boundary_f1(pred, gold, tol=0.030):
    """Greedy nearest-first 1-to-1 matching within +/- tol seconds.

    Greedy is optimal here: when tol is below the minimum inter-boundary
    gap, the match graph decomposes into disjoint intervals, so no
    exchange of assignments can increase the matching size.
    """
    unused, tp = set(range(len(gold))), 0
    for p in sorted(pred):
        cand = [(abs(p - gold[i]), i) for i in unused if abs(p - gold[i]) <= tol]
        if cand:
            unused.discard(min(cand)[1])
            tp += 1

    precision = tp / len(pred) if pred else 0.0
    recall    = tp / len(gold) if gold else 0.0
    if precision + recall == 0:
        return 0.0, precision, recall
    return 2 * precision * recall / (precision + recall), precision, recall
Engineering deep dives

Four problems that took real debugging

Anyone can list technologies. These are the failures I actually hit and how I reasoned through them.

The stale cache bug that only appeared in production
Symptom

PhishGuard kept returning "safe" for a domain that had already been reclassified as malicious. Locally it was always correct. In production it was correct roughly half the time — which is the worst possible failure mode, because it looks like flakiness rather than a bug.

Diagnosis

The Redis cache key was the URL alone. When I changed the scoring pipeline — new heuristic weights, a different RAG retrieval depth — every previously cached verdict became a silent lie. The cache had no idea the function that produced its values had changed underneath it. Locally I always started with a cold cache, which is exactly why I never saw it.

Fix

Versioned the cache key: phish:v{PIPELINE_VERSION}:{sha256(url)}, where the version is derived from the scoring config. A pipeline change now invalidates the whole namespace atomically, and old entries age out on their own TTL instead of needing a flush.

What I took from it

A cache key must identify the function, not just the input. If the code that computes a value can change, its identity belongs in the key. I now treat any cache without a version component as a latent correctness bug.

Why my first cross-validation split was quietly cheating
Symptom

An early version of the segmentation model scored beautifully in cross-validation and then fell apart on a held-out subject. The gap was far too large to be variance.

Diagnosis

I was splitting on utterances, not on subjects. Multiple recordings from the same speaker were landing in both the training and validation folds. The model wasn't learning where syllable boundaries are — it was partly learning what each speaker's vocal tract sounds like, then recognising that speaker at validation time. Textbook leakage, and completely invisible in the metrics.

Fix

Rebuilt the pipeline around leave-one-run-out partitioning, where the fold boundary is the subject. Scores dropped immediately — which was the point. The lower number was the honest one, and it became the baseline every later improvement was measured against.

What I took from it

The unit of independence, not the unit of data, defines the split. When a result looks better than it should, I now check the partitioning before I celebrate. Being suspicious of my own good numbers is the single habit that has saved me the most.

Hunting memory leaks through 4,000 lines of inherited C
Symptom

A bacterial-growth simulation the lab depended on would consume progressively more memory across long runs and eventually get killed by the OS. Nobody currently in the lab had written it.

Diagnosis

Ran it under Valgrind to get the leak sites, but the stack traces all bottomed out in the same handful of monolithic functions — several hundred lines each, with allocation and control flow deeply interleaved. Knowing where the leak surfaced said very little about which path had failed to free.

Fix

Refactored before fixing. Decomposed the monoliths into single-purpose functions with one clear ownership rule each: whoever allocates, frees, and no buffer crosses a function boundary without an explicit transfer of ownership. That restructuring made three leaks obvious by inspection and collapsed a large block of duplicated allocation logic into one path. Valgrind then reported clean across the full suite.

What I took from it

Sometimes the fastest fix is a refactor. I resisted restructuring at first because it felt like scope creep. But the leaks were a symptom of unclear ownership, and no amount of targeted patching would have addressed that. Structure is the fix.

Class imbalance: when 96% accuracy means the model learned nothing
Symptom

The first version of my segmentation head hit 96% frame-level accuracy on the first epoch and then stopped improving. Suspiciously good, suspiciously fast.

Diagnosis

Roughly 4% of frames are boundaries. The model had found the degenerate optimum — predict "not a boundary" everywhere — which is 96% accurate and completely useless. Plain BCE gave it no reason to do anything else, because the gradient was dominated by an enormous mass of trivially-correct negatives.

Fix

Two changes. Switched to focal loss (α = 0.25, γ = 2.0), which exponentially down-weights easy, confidently-correct examples so the rare positives actually move the gradient. Then stopped tracking accuracy entirely and evaluated on boundary F1 under the 30 ms tolerance — the metric that reflects what the model is for.

What I took from it

A metric that can be maximised by doing nothing is not a metric. On any imbalanced problem the first question is what the trivial baseline scores. If it scores well, the metric is wrong before the model is.

WHERE THE MATH SHOWS UP

Not decoration — load-bearing

Intermediate linear algebra is what makes attention legible: a transformer block is a sequence of projections and a softmax-weighted change of basis. Reading VG-HuBERT's architecture and knowing where to graft a head onto it required seeing it that way.

Advanced calculus is the spectrogram above — every column is a windowed Fourier transform, and the window length is a time–frequency resolution trade-off you have to choose deliberately. It is also why focal loss made sense as a fix rather than a thing to try: reshaping a loss surface so an overwhelming class stops dominating the gradient.

Calculus-based statistics and probability gave me the paired test, the effect size, and the instinct to distrust a cross-validation score that looks too good.

Abstract algebra and discrete mathematics are the proof discipline underneath both — structure-preserving maps, symmetry and equivariance, and the habit of establishing that something holds rather than checking that it seems to. The greedy matching argument in the widget above is that habit showing up in production code.
